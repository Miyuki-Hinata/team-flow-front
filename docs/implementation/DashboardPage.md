# DashboardPage

## 何を作ったか
朝一番の状況把握を目的とした 1 画面。挨拶タイトル + 日付、サマリカード×3（担当患者 / 本日のタスク / 未読お知らせ）、2 列の詳細（未読お知らせ / 本日の要対応患者）で構成する Dashboard の本格実装。

初期のフェーズ1では未読お知らせ×3件のみを出す最小構成だったが、本フェーズで README のダッシュボード仕様に合わせて完成させた。

## なぜこの設計にしたか
- **サマリカードは Dashboard 内に閉じた**：他画面で使う予定がない軽量な表示コンポーネント。汎用化しても呼び出し元がなく、逆に読みにくくなる。将来他画面でも同じ集計指標を出すことになったら `components/ui/SummaryCard.tsx` に切り出す方針。
- **並列取得 + 単一 Loading ゲート**：`announcements === null || myTasks === null` で 1 つの Loading を出す。個別に spinner を出すよりレイアウトが安定し、CLS を抑えられる。
- **本日の要対応患者 = 自分のタスクから逆引き**：`Patient` に「緊急」フラグが乗っていないので、「未完了 & 期限が今日以前」のタスクを持つ患者をユニーク化する形で抽出。バックエンド API を追加しなくても既存エンドポイントで実現できる。
- **PatientCard を再利用し Link で包む**：PatientCard は「表示のみ」設計なので、遷移責務は外に置く一覧ページと同じパターンを踏襲。
- **担当患者 = my-tasks のユニーク患者**：README の「担当患者」を厳密に定義しにくいため、実務的な「自分にタスクが割り当てられている患者」で近似。

## どのお手本に倣ったか
- **PatientCard.tsx**：`SummaryCard` を「表示のみ・遷移は Link に委譲」の型で書いた。`type SummaryCardProps` の分割代入受け取りも同じ。
- **AppLayout.tsx**：Loading 中は何も描画せず、揃ってから本体を描画する分離ポリシー。
- **AISummaryCard.tsx**：state を持たない props ドリブンの表示コンポーネントとしての骨格。

## 使用した theme トークン
- `spacing.md` / `.lg` / `.xl` — グリッドギャップ・カードパディング・セクション間の余白
- `radius.lg` — サマリカードの角丸
- `colors.surface.raised` / `border.default` / `border.strong` — カード土台 + ホバー強調
- `colors.text.primary` / `.secondary` — 大数字と補助ラベル
- `fontSize.xxl` / `.lg` / `.md` / `.sm` — 大数字（28px）・見出し（18px）・単位（16px）・ラベル（14px）
- `fontWeight.bold` — 大数字・タイトルの太字

## 面接で説明できるポイント
- **単一責任 + 再利用**：`SummaryCard` は表示だけ、遷移は Link、集計は Dashboard 側で `useMemo` に閉じる。責務境界がはっきりしている。
- **`useMemo` の使い所**：`myTasks` の変化にだけ反応して再計算するようにし、レンダー毎の重複計算を避ける。件数計算は軽いが、患者ユニーク化（Map 操作）を毎回走らせないため。
- **時刻無視の日単位比較**：`isDueToday` は `Date` の年月日 3 値で比較。ISO 文字列の substring 比較や getTime 引き算より意図が明確で、タイムゾーンずれの罠を避けやすい。
- **ロード状態の一元化**：state を `Type[] | null` にして `null` を「未取得」のマーカーにする書き方。boolean フラグを別途持つ実装より状態表現が少なく整合性を保ちやすい。
- **API 追加なしで README 仕様を満たした**：バックエンドに新エンドポイントを足すのではなく、既存 my-tasks の集計だけで「担当患者」「本日のタスク」「要対応患者」を計算するアプローチ。フロント側の判断で完結する範囲を優先。
