# AdminPage（管理ページ）

## 何を作ったか
管理者（admin）だけがアクセスできる `/admin` の管理ページ。ユーザー・部署・カテゴリ・プロジェクトの4種類をタブで切り替えて追加/編集/削除する。ページ自身は「どのタブを表示するか」と「部署一覧の共有」だけを担い、実際の CRUD は各セクションコンポーネントに委ねる。

## なぜこの設計にしたか

- **4セクションを縦積みからタブに変えた**：ユーザーが増えるほど下のセクション（カテゴリ・プロジェクト）までのスクロールが遠くなる。管理作業は一度に1種類しか行わず、部署とカテゴリを見比べる場面が無いため、排他表示のタブにして**どのセクションへも常に1クリック**で届くようにした。
  - アコーディオンも検討したが、複数開けるのが利点である一方、ユーザーを開いた瞬間にスクロール問題が戻る。「同時に見たい」要件が無い以上、タブのほうが構造に合う。
  - 既存の `ui/Tabs` をそのまま使用（お知らせ・患者詳細・受け持ち患者で既に使われており、操作感が揃う）。
- **`type AdminTab` を union 型にした**：`Tabs` がジェネリクス `<T extends string>` なので、union のまま `onChange` まで型が保たれ、`setActiveTab` にそのまま渡せる。`string` に潰れないのでタブ名のタイプミスは型エラーになる。
- **`key={activeTab}` でセクションを作り直す**：部署とカテゴリは**どちらも `MasterSection`** で同じ位置に描画される。React は「同じ位置・同じ種類の要素」を見つけるとインスタンスを再利用して props だけ差し替えるため、`useEffect(reload, [])`（マウント時1回）が再実行されない。結果、見出しだけカテゴリになって**中身は部署のまま**になる。`key` を変えて明示的に作り直すことで防いでいる。
- **部署一覧を親で保持する（lift state up）**：`ProjectSection` と `UserFormModal` の部署ドロップダウンが共有する。部署タブで追加/更新/削除されたら `onChanged` → `reloadDepartments` で取り直すので、タブを切り替えた時点で選択肢が最新になっている（リロード不要）。
- **ユーザーを先頭タブ＝初期表示にした**：入退職で最も更新頻度が高いため。
- **`renderActiveSection()` を関数に切り出した**：`switch` で網羅することで、`AdminTab` に値を足したとき分岐の書き漏らしを型で検出できる。

## どのお手本に倣ったか
- **AppLayout.tsx**：レイアウト（何をどこに置くか）とページ本体（中身の責任）を分離する考え方。ここでは「タブの制御」と「各セクションの CRUD」を分けている。
- **AISummaryCard.tsx**：`useState` で開閉/選択状態を持つときの素直な書き方。
- **MyPatientsPage.tsx（既存）**：`ui/Tabs` を `useState` と組み合わせて排他表示する使い方をそのまま踏襲。

## 面接で説明できるポイント
- **`key` は「リストの `map` で使うもの」ではない**：本来の役割は「この要素の同一性」を React に伝えること。今回のように**意図的に作り直させる**用途にも使う。`key` を付けないと部署→カテゴリの切替でデータが入れ替わらないバグになる、という実例で説明できる。
- **タブ vs アコーディオンの選択理由を言語化できる**：「同時に見たい要件があるか」「到達コストが一定か」「既存 UI との一貫性」の3点で比較して決めた。見た目の好みではなく、業務の進め方から導いている。
- **タブ化がページ1ファイルの変更で済んだ**：`UserSection` / `MasterSection` / `ProjectSection` は一切変更していない。「どのセクションを表示するか」はページの責任であり、セクション自身が知る必要がない——という責任分割ができていたため。
- **lift state up の実例**：当初 `ProjectSection` が自前で部署を fetch していたため、部署を追加してもプロジェクトのドロップダウンに反映されずリロードが必要だった。共有される状態を親に引き上げ、変更を `onChanged` コールバックで伝える形に直した。タブ化後も同じ仕組みがそのまま効いている。
