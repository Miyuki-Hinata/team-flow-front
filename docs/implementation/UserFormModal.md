# UserFormModal（ユーザーの追加/編集フォーム）

## 何を作ったか
管理ページのユーザー（職員）を追加・編集するモーダルフォーム。ログインID / 姓名 / かな / メール / 職種 / 部署 / パスワード / 管理者権限 の10項目を入力し、未入力チェックを通してから `onSubmit` で呼び出し側に渡す。追加と編集で同じコンポーネントを使い回す。

## なぜこの設計にしたか

- **なぜモーダルに分離したか**：部署（名前1項目）・プロジェクト（名前＋部署の2項目）は `MasterSection` / `ProjectSection` の行内編集で足りたが、ユーザーは10項目あり1行に収まらない。行内に押し込むと横スクロールか極端な縦伸びになるため、既存のお手本 `Modal` に載せた。
- **追加と編集を1コンポーネントで兼ねる**：`user: User | null` の1つの props で切り替える（`null` = 追加）。見出し・パスワードの必須判定・ヒント表示はすべて `user` の有無から導出しており、分岐は3箇所だけ。フォームを2つに分けると項目追加のたびに片方だけ直し忘れるため、あえて1つにまとめた。
- **`useEffect([isOpen, user])` で毎回初期化する**：`Modal` は `isOpen=false` のとき描画しないだけで、親に残った state は消えない。初期化しないと「Aさんを編集 → 閉じる → 追加を押す」で **Aさんの値が残ったフォームが開く**。開くたびに流し込むことでこれを防ぐ。
- **パスワードは編集時も必ず空から始める**：既存パスワードはハッシュしか無く復元できない。空欄のまま保存すればサーバー側（`UserService.updateUser`）が「変更しない」と扱うため、空が正しい初期値になる。編集時のみ「変更しない場合は空欄のままに」というヒントを出す（新規では誤解を招くので出さない）。
- **入力チェックはコンポーネント側に持つ**：サーバーでも検証されるが、往復する前に画面で気づけるほうが速い。`errors: Record<string, string>` を1つの state で持ち、`FormField` の `error` に渡す。パスワードの必須判定だけ `!user`（＝新規のとき）に限定している。
- **「管理者権限」チェックボックス ⇄ `level`**：サーバーは `User.isAdmin()` が `level == 2` で判定する内部表現だが、画面に「レベル2」と出しても意味が伝わらない。UI は真偽値のチェックボックスにし、`utils/user.ts` の `LEVEL_ADMIN` / `LEVEL_MEMBER` で変換する。
- **職種の選択肢は対応表から生成**：`roleLabel` の全キーを `roleOrder` 順に並べて `options` を作る。職種を決め打ちで列挙しないので、`Role` が増えても自動で選択肢に載る。
- **`departmentId` は `number | null`**：省略（`?`）ではなく明示的な `null` にしたのは、編集で「部署あり → 部署なし」に変えるとき、JSON にキーが無いとサーバーが「変更なし」と区別できないため。

## どのお手本に倣ったか
- **Modal.tsx**：`isOpen` / `onClose` を受け取り、閉じる責任は呼び出し側に置く汎用化パターンをそのまま利用（自前でオーバーレイを作らない）。
- **AISummaryCard.tsx**：`type UserFormModalProps = {...}` で型を定義し、`({ isOpen, onClose, ... }: UserFormModalProps)` と分割代入で受け取る流儀。
- **PatientCard.tsx**：色・余白をすべて theme トークンから引き、ハードコードしない。
- **ProjectSection.tsx（同フォルダ）**：部署の選択肢を自分で fetch せず `departments` を props で受け取る方針（親が保持して共有する）。

## 使用した theme トークン
- `spacing.xs` / `.sm` / `.md` — フォーム項目間・ボタン間・チェックボックスとラベルの間隔
- `colors.text.primary` — 見出しとチェックボックスのラベル
- `colors.text.secondary` — パスワード欄の補足文（Hint）
- `fontSize.lg` / `.xs` — モーダル見出し / 補足文
- `fontWeight.bold` — モーダル見出し

（Input / Select / Checkbox / FormField / Button の内部トークンは各コンポーネントに委譲。）

## 面接で説明できるポイント
- **同じ DTO を作成と更新で使い回すときの検証の置き場所**：サーバーの `UserRequest` は作成・更新で共用されているため、`password` に `@NotEmpty` を付けると「編集時は空欄OK」が表現できない。そこで DTO からアノテーションを外し、必須チェックを `createUser` の中へ移した。フロントの `validate()` が `!user` で分岐しているのはこのサーバー仕様と対になっている。
- **`isBlank()` ガードが無いと起きる事故**：修正前の `updateUser` は無条件に `passwordEncoder.encode(request.getPassword())` していた。空文字を渡しても BCrypt はエラーを出さず正常に見えるハッシュを作るため、**その職員が二度とログインできなくなるのに誰も気づけない**。空欄なら触らない、という分岐で塞いだ。
- **モーダルの state は「閉じても消えない」**：React の state はアンマウントされない限り残る。`Modal` は `if (!isOpen) return null` で中身を描画しないだけなので、フォームの値は親（このコンポーネント）に残り続ける。`useEffect` による明示的な初期化が必要な理由をこの仕組みから説明できる。
- **内部表現を UI に漏らさない**：`level` という数値は DB とサーバーの都合。画面には「管理者権限を付与する」というチェックだけを見せ、変換は `utils/user.ts` に閉じ込めた。`utils/role.ts` の `roleLabel`（内部値 → 表示名）と同じ考え方。
