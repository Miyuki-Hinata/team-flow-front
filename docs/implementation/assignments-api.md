# api/assignments.ts

## 何を作ったか
受け持ち患者 API（`/api/me/assigned-patients`）のフロント側クライアント。取得（GET）と集合置換更新（PUT）の2関数。

## なぜこの設計にしたか
- **`fetchWithAuth` を使う**：既存 api/*.ts と同様、401（アクセストークン切れ）で自動リフレッシュ&1回リトライする共通ラッパに乗せる。認証の作法を1箇所に集約する。
- **戻り値型を明示（`Promise<Patient[]>`）**：既存モジュールは `response.json()` を無型で返しているが、CLAUDE.md §2「型を省略しない」に従い明示した。呼び出し側（useState / hook）の型安全につながる。
- **GET と PUT でエラー処理の粒度を変えた**：GET は表示専用で失敗時は上位の Loading/EmptyState に委ねられるため最小限。PUT は「更新の成否」をユーザーに伝える必要があるため、`createPatient` と同じく 401＝セッション切れ／その他＝サーバメッセージ優先＋フォールバックの二段構えにした。
- **PUT の戻り値でサーバの最新一覧を受ける**：サーバが置換後の `Patient[]` を返すので、呼び出し側は再フェッチ不要（往復1回で状態を同期）。

## どのお手本に倣ったか
UI コンポーネントではないため §1 の4お手本（AISummaryCard 等）ではなく、既存 **api モジュール（`patients.ts` / `tasks.ts`）** の書き方を踏襲：`fetchWithAuth` + `API_BASE_URL` + Bearer ヘッダ、エラー時の try/catch フォールバック。

## 使用した theme トークン
なし（API 層のため見た目に関与しない）。

## 面接で説明できるポイント
- **集合置換（PUT）の冪等性**：`patientIds` を差分ではなく最終状態として送るので、リトライ・二重送信に強い。空配列＝全解除も同じ経路で表現できる。
- **戻り値でサーバ状態を返す設計**：楽観更新ではなくサーバ確定値を採用し、フロントとDBの乖離を防ぐ。往復も1回で済む。
- **認証の関心の分離**：トークン更新・401リトライは `fetchWithAuth` に閉じ込め、この層はドメイン（受け持ち）に集中している。
